# Сценарии работы сервиса

Статус: требования к будущей первой версии. Участник - исследователь. В каждом Job выбирается один источник, станция, компоненты и период.

Связь частей программы: запрос → Job → Dispatcher → Registry → Tool → ToolResult. Job - задание, Dispatcher запускает его, Registry находит модуль источника, Tool получает данные, ToolResult возвращает результат или ошибку. Не меньше двух адаптеров реализуют одинаковый контракт; новый адаптер добавляется без изменения Dispatcher.

Общие правила: сохраняем источник, станцию, время в UTC, компоненту, единицу и значение. Отсутствующее значение обозначаем null, а не нулём. Числа не исправляем автоматически. Неизвестный часовой пояс или обязательная единица - причина отклонить ответ, а не угадывать. Ошибки API имеют единый формат: код, понятное сообщение, детали и correlation ID - метку для поиска записей в журнале. Подробная схема и ограничения размера будут закреплены в описании API на практике 2.

## Сценарий 1. Запустить сбор измерений

**Участник:** исследователь. **Цель:** получить данные нужной станции за выбранный период.

**Основной порядок:**

1. Исследователь отправляет через API источник, станцию, компоненты и период.
2. Сервис проверяет запрос и создаёт Job в состоянии Created.
3. Программа переводит Job в Downloading и получает данные источника.
4. В состоянии Processing проверяет данные и приводит их к общему виду.
5. Сохраняет результат и переводит Job в Completed.

**Критерии приёмки:**

- Дано: источник подключён и запрос верный. Когда: запрос принят. Тогда: возвращён номер Job, по которому можно узнать состояние и получить результат.
- Дано: Job завершился успешно. Когда: запрошен результат. Тогда: видны данные, источник, станция, единицы и отчёт о проверке.
- Дано: клиент повторил тот же запрос с тем же ключом идемпотентности. Когда: сервис получил повтор. Тогда: возвращён прежний Job, повторного сбора нет.
- Дано: с тем же ключом присланы другие параметры. Когда: сервис получил запрос. Тогда: возвращён конфликт, новый Job не создан.

## Сценарий 2. Скачать собранные данные

**Участник:** исследователь. **Цель:** получить набор для анализа или обучения модели.

**Основной порядок:**

1. Исследователь указывает номер завершённого Job и формат CSV или JSON.
2. Сервис читает сохранённый результат, не обращаясь к источнику заново.
3. Возвращает данные вместе с описанием источника, единицами и отчётом о качестве. Для CSV отчёт и описание могут выдаваться отдельными файлами.

**Критерии приёмки:** 

- Дано: Job в Completed. Когда: запрошена выгрузка. Тогда: файл читается в выбранном формате, пропуски отличимы от нулей, происхождение данных сохранено.
- Дано: Job ещё выполняется. Когда: запрошен итоговый файл. Тогда: возвращена ошибка «Результат ещё не готов».
- Дано: номер Job неизвестен. Когда: запрошен результат. Тогда: возвращена ошибка «Задание не найдено».

## Сценарий 3. Сравнить значения измерений из двух источников

**Участник:** исследователь или аналитик. **Цель:** увидеть различия между значениями одной измеряемой величины, полученными из двух источников.

**Основной порядок:**

1. Пользователь выбирает два ранее собранных набора данных и период сравнения.
2. Система проверяет, что наборы относятся к одной станции и одной измеряемой компоненте, а значения представлены в одинаковых единицах.
3. Система находит записи с совпадающим временем измерения.
4. Для каждой пары показывает время, значения из обоих источников и их разность: значение первого источника минус значение второго.

**Критерии приёмки:**

- Дано: выбраны сопоставимые наборы, содержащие измерения с совпадающим временем и числовыми значениями. Когда: пользователь запускает сравнение за выбранный период. Тогда: система показывает таблицу совпавших по времени измерений и рассчитанную разность для каждой пары. Записи без пары или с пропущенным значением в расчёт не включаются.
- Дано: наборы относятся к разным станциям или компонентам, имеют разные единицы либо не содержат подходящих пар измерений. Когда: пользователь запускает сравнение. Тогда: система объясняет причину и не рассчитывает разности.

## Сценарий 4. Источник отказал в доступе

**Участник:** исследователь. **Цель:** понять, почему сбор не состоялся.

**Основной порядок:**

1. Во время Downloading источник возвращает ошибку 401 - отказ в доступе.
2. Модуль прекращает запросы к этому источнику без повторов с теми же данными доступа.
3. Сервис переводит Job в Failed и сохраняет безопасное описание причины.

**Критерии приёмки:**

- Дано: источник вернул 401. Когда: ответ обработан. Тогда: Job в Failed, пользователю показано «Источник отказал в доступе», секретный токен не попадает в ответ или журнал.
- Дано: ошибка доступа. Когда: исследователь проверяет Job. Тогда: в диагностике указаны источник и причина ошибки.

## Сценарий 5. Источник недоступен или прислал неверные данные

**Участник:** исследователь. **Цель:** получить понятную ошибку вместо зависания или испорченного результата.

**Основной порядок:**

1. Программа ждёт ответ не дольше установленного срока (timeout).
2. При временном сетевом сбое повторяет запрос ограниченное число раз с задержкой; точную политику определим для выбранных источников.
3. Проверяет структуру и размер полученного ответа.
4. Если данные получить или проверить нельзя, переводит Job в Failed, сохраняет причину и не публикует набор как готовый.

**Критерии приёмки:**

- Дано: источник не отвечает. Когда: время и попытки исчерпаны. Тогда: Job в Failed, показано «Источник временно недоступен», бесконечных повторов нет.
- Дано: вместо данных пришла страница HTML или нарушена схема. Когда: ответ проверен. Тогда: Job в Failed с сообщением о неверном ответе; HTTP 200 сам по себе не означает успеха.
- Дано: ответ больше разрешённого размера. Когда: достигнут лимит чтения. Тогда: получение остановлено и записана ошибка размера.

## Сценарий 6. Отклонить неверный запрос пользователя

**Участник:** исследователь. **Цель:** исправить параметры и запустить корректный сбор.

**Основной порядок:**

1. Пользователь отправляет запрос с неверным периодом, неизвестным источником или неподдерживаемой компонентой.
2. Сервис проверяет параметры до запуска внешнего запроса.
3. Возвращает описание ошибки с указанием поля.
4. Пользователь исправляет запрос и отправляет снова.

**Критерии приёмки:**

- Дано: начало периода позже конца. Когда: пришёл запрос. Тогда: возвращена ошибка периода, Job не создан, источник не опрашивается.
- Дано: источник отсутствует в Registry. Когда: пришёл запрос. Тогда: возвращена ошибка неизвестного источника; произвольный URL не принимается.

## Состояния Job и разрешённые переходы

- Created - запрос проверен, задание создано и ожидает исполнения.
- Downloading - программа получает данные из внешнего источника.
- Processing - программа проверяет и приводит данные к общему виду.
- Completed - проверенный результат и отчёт сохранены.
- Failed - задание завершилось ошибкой.

Разрешены только переходы:

- Created → Downloading;
- Created → Failed - программа не смогла начать исполнение;
- Downloading → Processing;
- Downloading → Failed;
- Processing → Completed;
- Processing → Failed.

Completed и Failed - конечные состояния. Другие переходы отклоняются без изменения Job. Результат и состояние Completed сохраняются одной неделимой операцией: не должно появиться «готовое» задание без результата. Отмена и отдельная очередь с брокером в первую версию не входят. После Failed новый запуск создаётся отдельным запросом с новым ключом; старый Job остаётся в истории.

## Что предложил ИИ

**Промпт для разбора:** «Мы делаем агрегатор геофизических данных. Первая версия собирает геомагнитные измерения по источнику, станции и периоду. Найди ещё 3 способа сломать основной сценарий: получение данных, проверка и сохранение результата. Объясни последствие и предложи проверяемую защиту».

**Предложения ИИ и решения в проекте требований:**

1. Клиент повторил запрос после потери связи, и сбор запустился дважды. Принято в требования: ключ идемпотентности. Это предотвращает повторную работу; одинаковый повтор возвращает прежнее задание (сценарий 1).
2. После преобразования потерялись единицы или станция, и смешались разные измерения. Принято в требования: хранить происхождение, компоненту и единицу каждого ряда. Это предотвращает смешивание несопоставимых данных; неизвестные обязательные метаданные не угадываются (общие правила).
3. Источник прислал данные только за часть периода, но результат выглядит полным. Принято в требования: отчёт о покрытии. Он позволяет отличать успешную загрузку от полноты измерений; при известном шаге перечисляются пропуски, иначе полнота отмечается как неизвестная (сценарий 3).

Решения отражены в этом документе как требования к будущей реализации. Они не означают, что соответствующие функции уже написаны или проверены.
